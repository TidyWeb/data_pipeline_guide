01 / THE SPINE

Five stages, five different jobs

Every piece of data analysis you will ever do walks the same route. The stages are genuinely different work, done with different tools, and most confusion about “which library do I use” dissolves the moment you know which stage you are standing in.

Scroll sideways to follow the whole route →

The common trap

Reaching for the wrong stage

“My chart looks wrong” is almost never a charting problem. It is usually a shaping problem wearing a chart’s clothes. Walk back up the pipeline until you find the stage where the truth changed.

The inherited stage

Someone else’s decisions

You will normally arrive at stage three. Stages one and two were settled by people who were not thinking about your question. Their choices set a hard ceiling on what you can find.

The direction of travel

Narrowing, always

Four hundred million rows become thirteen. Thirteen become one sentence. One sentence becomes one picture. Every stage throws material away — deliberately.

02 / COLLECTION

The only stage you can never repair

A till scan. A form submission. A sensor reporting. A line written into a server log because someone loaded a page. This is where data quality is decided, and no amount of clever Python later will undo a decision made here.

Is it trustworthy?

Quality

Accurate, complete, consistent — and does it actually measure the thing it claims to measure?

If the form offered a free-text box for “county”, you will receive Derbyshire, derbyshire, Derbys, DBY and N/A forever. You can standardise the spellings. You cannot recover what the person meant by N/A.

How fine-grained is it?

Richness

Also called granularity or resolution. One row saying March sales: £40,000 is poor. A row per transaction carrying a timestamp, item, branch and payment method is rich.

If the sensor samples once an hour, the minutes are gone. They were never written down, and nothing downstream can invent them.

The practical consequence: when you are ever in a position to influence collection, argue for the finest grain you can afford to store. You are not deciding what today’s question needs. You are deciding what every future question will be permitted to ask.
And it is worse than merely lossy. Collapsing detail does not only remove information — under the right conditions it can reverse the conclusion, so that a trend visible in every subgroup runs the opposite way once the subgroups are pooled. That effect has a name, Simpson’s paradox, and it is examined properly in section 08. Hold the thought until then; for now, note only that grain is not a matter of resolution alone. It can decide which answer you get.
03 / STORAGE

Where SQL actually lives

The records have to sit somewhere, and overwhelmingly that somewhere is a database. The conceptual point is one of scale: a database holds vastly more than you want, and it is not going to fit on your laptop.

So whoever told you SQL is vital for data analysis was right — and your course is not wrong to leave it out. It is teaching the other half. A course that runs CSV → pandas → chart is a real, complete, working pipeline. It is simply the version where somebody else already ran the SQL and handed you the extract.
04 / SHAPING

The same thought, said in two places

Shaping means filtering, sorting, joining tables together and summarising. The thing that confuses learners is that it happens twice, in two languages, doing largely the same work — because it happens on two sides of a network cable.

Shaping at source

SQL

Runs inside the database, before the data reaches you. Its job is to reduce an enormous store down to a manageable extract.

Filtering, joining, grouping, summarising — across volumes far too large to hold in memory.

Shaping in memory

pandas

Runs on your machine, after the extract has arrived. Its job is the detailed, exploratory, iterative work on something that fits in RAM.

Filtering, joining, grouping, summarising — plus cleaning, reshaping, and everything that feeds a chart.

Over there, in the databaseSQL
WHERE branch = 'Nottingham'
Over here, in memorypandas
df[df["branch"] == "Nottingham"]

That overlap is good news, because it means the concepts transfer completely and only the syntax differs. Both are saying: keep the rows where this is true, drop the rows where it is false. You already know that idea from writing a loop with an if inside it — the two lines above are that same loop-plus-if, written as shorthand by people who got tired of typing it out.

Learn SQL after, not instead. Because you will already own the concepts, you will pick up the syntax in a fortnight.On the gap in the syllabus
05 / SHAPE

Shape is just a tuple of sizes

This is the idea that unlocks NumPy, and it is far smaller than the word makes it sound. Shape means: how many dimensions the data has, and how big each dimension is. Nothing more.

Scroll sideways to climb the whole ladder →

What the error is telling you

“Shapes not aligned”

When NumPy shouts about shapes, it is saying something mundane: you have asked it to line a 5×7 grid up against a 3×9 grid, and there is no sensible way to do that. Read the two shapes in the message and compare them position by position.

What makes it an array

The rule on top

An array is a nested list with one extra rule imposed: every box at the same level must be the same size, and everything inside must be the same type. No row of six beside a row of nine. No string hiding among the numbers.

06 / THE ENGINE

Why NumPy gave up flexibility

The rigidity looks like a restriction. It is actually the entire reason NumPy is worth having — and the reason is about memory, not about mathematics.

Where the C comes from, and why it is there at all

Nothing in this section asks you to learn C. But it is worth knowing that it is underneath you, because it explains the whole trick.

Fact one

Python itself is a C program

The thing that runs when you type python is an interpreter called CPython, written in the C language and compiled into machine code long ago.

So even a plain Python for loop is, underneath, C code reading your instructions one at a time and doing as it is told. That is true before NumPy appears anywhere.

Fact two

NumPy is not written in Python

It is a Python package — you install it with pip and import it like anything else — but its working parts are C, compiled before it ever reached your machine.

The Python you write is a thin steering layer sitting on top of that compiled code.

Fact three

The handover

When you write temperatures * 9/5 + 32, Python does not do the arithmetic. It sees the *, recognises a NumPy array, and hands the whole job downward: here is a block of a million numbers, here is the operation, get on with it.

Your interpreter did about three things. The C did a million.

Compiled versus interpreted — that is the whole difference. Compiled code has already been translated into machine instructions and runs flat out. Interpreted code, like the Python you write, is worked out line by line as it goes, which is what makes it pleasant to write and slow to execute. The scientific Python stack is built on one idea: write in the friendly slow language, execute in the fast unfriendly one — which only works if you hand work down in big uniform chunks rather than one item at a time. That condition is exactly why an array must be one type with no ragged edges.

What the rigidity changes in how you write

Speed is only half of it. The other half is that you stop writing loops — and that is the genuine mental shift NumPy asks of you.

The loop you would have writtenItem by item
fahrenheit = []

for c in temperatures:
    fahrenheit.append(c * 9/5 + 32)

# One trip round the loop
# per temperature.
The same thing, vectorisedWhole array at once
fahrenheit = temperatures * 9/5 + 32




# One line. All million values.
# The loop still happens — in C.
The shift in wording: you stop thinking “for each item, do this” and start thinking “do this to the whole thing”. The looping has not vanished. It has moved somewhere far below you, where it is cheap.
07 / THE FAMILY

Who does what, and who sits on whom

Four names get thrown at you at once. They are not competitors. They stack.

Upstream

SQL

When the data is bigger than your machine, or lives in a company system you have to ask nicely.

Underneath

NumPy

When the work is numerical, heavy and uniform. Also whenever you drop below pandas to fix something.

Daily driver

pandas

Nearly everything. Real tables where one column is names and the next is prices.

Last mile

Charting

Once the answer exists and needs to be seen by someone who will not read your code.

Which explains why NumPy is taught before you are convinced you need it. You will use pandas for nearly everything. NumPy is underneath, and you meet it face to face only when the work turns purely numerical — but its rules are leaking through the wrapper the entire time.
08 / VISUALISATION

A stage, not a decoration

Charts do a job tables cannot, and the reason is physiological rather than aesthetic: the eye detects shape faster than the mind reads numbers. But this is the most nuanced stage on the route, and it deserves three passes rather than one — because there are three separate ways to be misled here, and they fail in different directions.

Movement one

The numbers alone will fool you

Identical summary statistics can sit on top of completely different realities. Only the picture separates them.

Movement two

The grain alone will fool you

Pool the subgroups and the trend can run backwards. Both figures are arithmetically correct.

Movement three

The picture alone will fool you

A chart is a set of choices. Some of those choices manufacture a story that is not in the data.

Movement one

Identical statistics, four different worlds

Francis Anscombe built the quartet in 1973 to argue that statisticians were leaning too hard on computation. Four datasets of eleven points each, agreeing to two decimal places on the mean of x, the mean of y, the variance of both, the correlation coefficient and the regression line. Feed any of them into a stats package and the same summary comes back.

What the four are doing

Reading the panels

I is a genuine, noisy linear relationship — the line is a fair summary of it. II is a clean curve: the relationship is real and strong, but it is not a line, so a line is simply the wrong model.

III is a perfect straight line plus one distant point, and that point tilts the fitted line until it misses every real observation. IV has ten points sharing one x value and a single point far to the right, and that lone point is dictating the whole slope. Remove it and there is no relationship left to fit.

The modern remake

The Datasaurus Dozen

Justin Matejka and George Fitzmaurice later built a set of thirteen datasets that agree on their summary statistics to two decimal places — among them a star, a circle, a set of parallel lines, and a dinosaur.

It is the same lesson as Anscombe with the volume turned up, and it is worth looking at because the laugh is what makes the point stick. If a dinosaur and a star can share a mean, a variance and a correlation, those three numbers were never describing the shape of anything.

Note the direction of Anscombe’s argument. It is not that pictures lie. It is the reverse: here the numbers lied and the picture told the truth. Four different realities, one identical set of statistics. Hold that, because the next two movements run the other way.
Movement two

When pooling reverses the answer

This is the hinge of the whole guide, and it reaches back to section 02. Aggregation does not merely lose detail. Under the right conditions it inverts the conclusion — and both the pooled figure and the subgroup figures are arithmetically correct at the same time.

First, the word

What pooling means

Pooling means you throw two groups into one pile and count them together as if they were one group.

Not averaging the two percentages. Adding up the raw numbers — all the successes, all the patients — and working out one percentage from the combined pile.

Then, the surprise

What can happen when you do

A result that holds in every group can reverse when you combine the groups.

Nothing is done to the data. Nobody cheats. Both figures are calculated correctly. You simply get a different answer depending on whether you keep the groups separate or throw them in one pile. That situation has a name: Simpson’s paradox.

The case: two kidney stone treatments

Two treatments, A and B, each given to 350 patients. Patients are split into two kinds: small stones, which are easier to treat, and large stones, which are harder. Success rates were recorded for each kind separately, and then for everyone together.

The arithmetic, in full

Pooling is addition, and nothing else. Add the successes, add the patients, divide.

Treatment ATreatment B
Small stones81 successes out of 87  →  93%234 successes out of 270  →  87%
Large stones192 successes out of 263  →  73%55 successes out of 80  →  69%
Pooled
add the successes, add the patients		81 + 192 = 273
87 + 263 = 350
273 out of 350  →  78%		234 + 55 = 289
270 + 80 = 350
289 out of 350  →  83%

Why A loses despite winning both

Look at who each treatment was actually given to.

A’s pooled score is dragged down towards the 73%, because three quarters of A’s patients were large stones. B’s pooled score is pulled up towards the 87%, because three quarters of B’s patients were small stones.

Pooling hid the fact that the two treatments were not given the same mix of patients. The combined figure ends up reporting the difficulty of the caseload instead of the quality of the treatment.What went wrong, in one sentence

The same thing, at scale: Berkeley, 1973

Graduate admissions figures for the University of California, Berkeley appeared to show men being admitted at a notably higher rate than women. The two charts below show the same admissions, counted two ways. The first pools every department together. The second keeps them apart.

The six departments shown are the largest six, which is the set this case is normally examined through. Note carefully what each chart measures: the pooled chart shows rates, and the department chart shows how many people applied, with the admitted portion filled in solid. That second measurement is the one the pooled figure throws away, and it is the one that explains everything.

The practical test: before trusting any pooled figure, ask what groups sit inside it and whether those groups appear in different proportions. If they do, calculate the same thing inside each group. If the two answers disagree, the disagreement is the finding.
Movement three

A chart is a set of choices

Every plot involves decisions that are invisible in the finished image: where the axis starts, which rows were included, what the date window is, whether a quantity is encoded as length or as area. Some of those decisions manufacture a story that is not in the data — sometimes deliberately, and often not.

Trick

Dual axes

Two series, two independently scaled y axes. Slide either scale and you can make almost any pair of lines appear to move together.

Trick

The chosen window

Start the date range at a trough and end it at a peak. Every point plotted is real; the window did the arguing.

Trick

Area for length

Encode a value as the width of a circle or icon and the eye reads its area. Double the number, quadruple the ink.

Trick

Perspective

A tilted three-dimensional pie makes the nearest slice look largest regardless of what it holds.

Those four are cosmetic and mostly easy to catch once you know the moves. The serious failure is different, and it is a failure of omission — a chart that is honestly drawn from the wrong rows.

The scenario

Cape Canaveral, the night of 27 January 1986

The space shuttle Challenger is due to launch the next morning. The forecast overnight temperature at the launch pad is far colder than any previous shuttle flight has ever experienced.

Engineers at the firm that builds the solid rocket boosters believe this is dangerous. The boosters are sealed by rubber rings called O-rings, and rubber stiffens as it gets cold. A stiff O-ring seals more slowly, and if it fails, burning gas escapes from the side of the booster. They want the launch delayed.

They join a late-night conference call with NASA to make that argument, and they bring charts showing O-ring damage on previous flights. The charts below are the shape of what they presented, and the shape of what they could have presented instead.

The chart they took into the meeting

Seven points, and no argument

Only the flights that had suffered damage were plotted. Those seven points sit scattered about with no visible relationship to temperature, so the chart appears to say that cold has nothing to do with it. The launch was approved.

The chart they could have taken

Add every flight, and the pattern arrives

The flights that came back with no damage were left off the first chart entirely, and every one of them was a warm launch. Put them back and the point becomes obvious: warm launches almost never suffered damage, and cold launches almost always did. No cold launch had ever come back clean.

Challenger launched the next morning at 36°F, colder than anything on either chart. An O-ring failed, and the vehicle broke apart 73 seconds into flight, killing all seven crew. The Rogers Commission found the temperature relationship in the data afterwards — it had been there the whole time, sitting in the rows nobody plotted. Edward Tufte later wrote about the presentation itself at length, and it remains the strongest argument that visualisation is a discipline with a duty of care rather than a finishing flourish.

The omission is the hardest failure to catch, because there is nothing on the page to look at. A truncated axis leaves a visible tick mark. A missing row leaves nothing at all. The only defence is asking, every time: what was filtered out before this was plotted, and would including it change the shape?
Neither the summary nor the chart is authoritative on its own. Compute it, plot it, then check that the two agree — and when they disagree, that disagreement is the most informative thing in front of you.Closing position for stage five

That is not an argument for distrusting everything. It is an argument for staying alive to what you are looking at, and for viewing anything important from more than one angle before you put it up. A disagreement between the number and the picture is not an inconvenience to be smoothed over. It is a signal, and it usually points back upstream to a decision about grain.

09 / CANVAS

Questions to ask at the start of anything

Run these before you write a line. They locate you on the route, which tells you what the problem is actually made of.

  1. Which stage am I standing in? Collection, storage, shaping, analysis or visualisation. Nearly every stuck moment is caused by treating one as another.
  2. What grain did I receive, and what grain does my question need? If the question needs finer than the data, stop. That answer does not exist.
  3. Was anything already aggregated before it reached me? If so, note what was lost and whether it can be re-extracted from further upstream.
  4. Does this fit in memory? If not, the shaping belongs in SQL, not pandas.
  5. What shape is this, right now? Say the tuple out loud. Most array errors are answered by that sentence alone.
  6. Am I writing a loop over something uniform and numeric? If yes, there is almost certainly a vectorised line that replaces it.
  7. Have I actually plotted it? Before trusting any mean, correlation or trend line.
Carry these four

The load-bearing ideas

Aggregation is a one-way street. Fine to coarse, always. Coarse to fine, never.

Shape is just a tuple of sizes, outermost first. Boxes within boxes, with the sizes written down.

An array is a list that gave up flexibility to buy speed. One type, no ragged edges, one unbroken block.

SQL and pandas are the same thought in two places. Learning one teaches you most of the other.

Every stage is a different job. Knowing which one you are standing in tells you which tool the problem is asking for.Closing principle
